## 详细说明与处理意见

### SEC-01｜密钥泄露（已修正：泄露的是上一个网站的旧密钥，非当前站点）
- 事实修正（用户确认）：.env.example 是上一个网站遗留的，里面的 DATABASE_URL/AUTH_SECRET 与当前站点不一致；当前站点的真实密钥在 .env.development（已被 .gitignore 忽略，git 全历史从未提交，未泄露）。
- 证据：首日提交 9b45a4a（2026-05-06）的 .env.example 含真实样式的 Supabase 连接串与 64 位 hex AUTH_SECRET，`git log -S` 确认从未删除；当前工作区 .env.example 仍是同一组值。
- 残余风险：无——旧站已下线、域名已失效（用户确认），泄露的旧密钥已无攻击目标。
- 处理意见：无需任何动作。仅剩顺手项：.env.example 改占位符（模板文件避免以后复用带真值进 git）。

### SEC-02｜credits 客户端可控（P0-紧急）
- 证据：src/app/api/ai/generate/route.ts:25-27,52-53 —— `const costCredits = credits`，注释明说"前端算好的积分直接使用"；video.tsx:704 客户端发送 credits。传 credits:0 即 0 积分调用。
- 处理意见：服务端按 model id + 参数（时长/分辨率/画质）从 pricing 配置独立计算应扣积分，客户端值仅作展示参考、一律不信任。这是资金安全的总闸，优先级最高的代码改动。

### SEC-03｜Replicate/MUSIC 任意透传（P0-紧急）
- 证据：replicate.ts:85-90 `predictions.create({ model, input })`，model 取自请求体 :21 仅非空校验；replicate.ts:269-272 `input = { ...input, ...options }` 全量展开；VIDEO/MUSIC 不送审核（route.ts:76 只审 IMAGE）。music.tsx:108 前端固定 10 积分只是展示。
- 处理意见：服务端维护可用模型白名单（复用 models.ts 的 apiModels 清单），拒绝白名单外模型；透传字段改白名单制；该通道纳入统一审核。

### SEC-04｜admin Server Action 无权限校验（P0-紧急）
- 证据：17 处 'use server' 写操作处理器（grant-credits:86-92、edit-roles:87-93、settings:46-52、set-plan:104-111、showcases/categories/prompts/posts/roles 各 add/edit）均只查"目标用户存在"或 getUserInfo 非空，不校验调用者角色；middleware（proxy.ts:43-47）对 /admin 只查 session 存在。Server Action 是公开 POST 端点，普通登录用户可直接调用给自己发积分、改全站配置。
- 处理意见：在每处 Server Action 处理器开头统一加 `requirePermission({ code: ... })`（页面层已有该函数，直接复用）；或抽一个 withAdmin 包装器统一套。17 处逐个补，grep `'use server'` 于 (admin) 目录即可枚举。

### SEC-05｜视频生成不送审核（P0-高）
- 证据：route.ts:76-89 审核条件 `mediaType === AIMediaType.IMAGE && trimmedPrompt`；VIDEO 分支 :60-67 只校验 scene 枚举，:108 直达上游。DeepSeek 审核器（deepseek.ts:43）本身也只是文本审核器。
- 处理意见：VIDEO（含 MUSIC）的文字 prompt 一并送 moderatePrompt；一行条件改动即可堵住入口①的视频部分。

### SEC-06｜参考图片无内容审核（P0-高）
- 证据：/api/upload/route.ts:31-40 与 /api/storage/upload-image/route.ts:43-49 只校验 MIME 和大小；全仓无任何图片内容审核实现；图片 URL 经 options.image_input → kie.ts:266-267 直达 KIE。
- 处理意见：接入图片审核（云厂商内容安全 API 或多模态模型判别），在上传接口同步拦截；短期可先对未登录/低信誉账号关闭参考图功能止血。

### SEC-07｜KIE 透传绕过已审 prompt（P0-高）
- 证据：kie.ts:184-201（generateImage）与 :280-294（generateVideo）的 excludeKeys 均无 'prompt'；用户在 options 里塞 prompt 字段会覆盖 :151-153 已审的 payload.input.prompt。
- 处理意见：两处 excludeKeys 补 'prompt' 及所有已单独处理过的敏感字段（first_frame_url、image_urls 等）；更彻底的做法是透传改白名单制（与 SEC-03 同一方案）。

### SEC-08｜IP 风控整体失效（P0-高）
- 证据：risk-control.ts:5 `import * as schema from '@/config/db/schema.sqlite'`（注释"修正导入路径"从模板带来 5 个月）；login_attempt/ip_blacklist 两表只在 schema.sqlite.ts:130/157 定义，schema.postgres.ts 中零匹配；catch 块 :164-171 console.error 后 return { allowed: true }，isIpBlocked/getLoginAttemptsCount 出错同样放行。auth 注册/登录钩子（config.ts:103-111,140-141）引用它，等于全失效。
- 处理意见：二选一——在 PG 建这两张表并改 import 到 postgres schema，或直接删掉该模块改用限流中间件（见 SEC-13）。同时把 fail-open 改 fail-closed 需慎重（否则 DB 抖动会锁死全站登录），建议：风控查询失败时降级为「限频按内存计数」而不是完全放行。

### SEC-09｜邮箱验证未强制（P1）
- 证据：requireEmailVerification 全仓零匹配；settings.ts:392-395 email_verification_enabled 默认 'false'；auth config 无 emailVerification 强制块；注册即用（config.ts:66-68），无 middleware 拦截；zh/common.json:34 的文案「注册后需完成邮箱验证」与实际不符。
- 处理意见：启用 better-auth 的 emailVerification.sendOnSignUp + require；开启后必须同时配置 resend_api_key，否则用户全被锁在门外（上线前用测试账号回归）。假邮箱域名注册问题可叠加一次性邮箱域名黑名单。

### SEC-10｜IDOR 聊天记录（P1）
- 证据：/api/chat/messages/route.ts:28-35 调 getChatMessages 未传 userId、未校验 chat 归属；chat_message.ts:54 userId 可选过滤，undefined 即不过滤。对照组 chat/info:22-24、chat/route.ts:61-63 都有归属校验，唯独 messages 漏了。
- 处理意见：与 info 路由同款三行校验即可（chat.userId !== user.id 则拒绝），最小改动。

### SEC-11｜SSRF 代理可绕过（P1）
- 证据：/api/proxy/file/route.ts:40-49 公开无鉴权 GET ?url=；已有 https 校验和私有 IPv4 字面量黑名单，但 isPrivateIPv4 要求 parts.length===4（127.1、2130706433、0x7f000001 均绕过）、未处理 IPv6（::1、fc00::/7）、:52-54 redirect:'follow' 可 302 跳内网、无 DNS 解析后复查。
- 处理意见：改为「解析域名 → 取全部 A/AAAA 记录 → 逐个校验非私有/非环回 → 再请求，且 redirect: 'manual' 逐跳复检」；或干脆下线该代理，改为对已上传到自己存储的 URL 放行。

### SEC-12｜审核链路健壮性（P1）
- 证据：deepseek.ts:31-54 fetch 无 timeout/AbortSignal（上游挂起会拖死 generate 接口）；route.ts:79 开关 prompt_moderation_enabled !== 'true' 即整条跳过（fail-open）；图片路径异常会 fail-closed 上抛（NSFW_MODERATION_FAILED）。
- 处理意见：fetch 加 AbortSignal.timeout(5000)；审核异常时按「拒绝生成」处理保持 fail-closed，不要静默放行；生产确保开关为 true 并加启动检查。

### SEC-13｜全站无限流（P1）
- 证据：仅 src/shared/lib/rate-limit.ts（内存 Map 最小间隔限流，重启清零、单实例有效），唯一使用点 /api/auth/[...all]/route.ts:18（getSession）；IP 取 x-forwarded-for 可伪造；/api/ai/generate、/api/proxy 等全部裸奔。
- 处理意见：引入基于 Redis/Upstash 的限流中间件，至少覆盖 /api/ai/generate、/api/upload、/api/proxy/file、/api/payment；与 SEC-08 的风控重建合并做。

### SEC-14｜注册无条件开放（P1）
- 证据：config.ts:66-68 emailAndPassword.enabled:true 无条件；getSocialProviders 仅 Google/GitHub（:221-241）；无邀请码/白名单（全仓零匹配）；前端表单开关 email_auth_enabled 默认 'true'（settings.ts:384-387）。
- 处理意见：与 SEC-09 联动——强制邮箱验证后假域名账号无法激活，成本已大幅抬高；如滥用再现，再加一次性邮箱域名黑名单或注册审批开关。

### SEC-15｜Trial 同 IP 限领口径修正（P1，认知修正）
- 证据：不存在 getUserCreditsCountByIp；实际 getUsersCountByIp（user.ts:73-84），config.ts:122-126 判断 `<= 5`——同 IP 前 5 个账号都可领初始积分，不是 1 个；注册侧 IP 限制依赖已失效的 risk-control（SEC-08）。
- 处理意见：阈值是否收紧为 1 由运营决定；更重要的是把注册频控从失效的 risk-control 迁到限流中间件（SEC-13）。

### SEC-16｜「先调用后扣费/并发双花」认知修正（P2）
- 核验结论：截图描述与实现不符。实际时序：先查余额（route.ts:92-95）→ 调上游（:108）→ 建任务时扣费（:131），ai_task.ts:18-35 任务插入与 consumeCredits 同事务；credit.ts:205-227 SELECT FOR UPDATE 行锁，:295 事务执行——并发双花已有防护。残余风险：并发第二个请求余额检查通过但扣费失败时，上游任务已创建（上游成本泄露，量级有限）。
- 处理意见：无需大改；可选优化是把余额预检查改为原子「预扣 + 失败返还」，彻底消除成本泄露窗口。真正的资金风险在 SEC-02，别把精力花在这条。

### SEC-17｜Stripe 认知修正（P2）
- 核验结论：截图「钱收了永不发货」与实现不符。实际：checkout 创建订单 PENDING 不发放（checkout/route.ts:257,277）→ webhook constructEvent 签名校验（stripe.ts:247-251）→ handleCheckoutSuccess 幂等 + paymentStatus.SUCCESS 才置 PAID 并按服务端订单的 creditsAmount 发放（payment.ts:139-247）。真实缺口：未比对实付金额与订单金额（payment.ts:162 只记录不校验）。
- 处理意见：在 handleCheckoutSuccess 增加 `paymentAmount >= order.amount` 一致性兜底校验，不一致则拒发并告警。
