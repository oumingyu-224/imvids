# 漏洞修改计划（安全 17 项）

> 配套文档：安全漏洞核验与处理意见.md（核验结论与证据）。本文件只写「怎么改」。
> SEC-01 无需处理（旧站已下线）、SEC-16 无需修改（双花已有防护），不在本计划列改造步骤。
> 实施顺序：第一批资金/权限 → 第二批审核入口 → 第三批纵深防御。

## 第一批：资金与权限（收益最大）

### SEC-02：服务端计算积分，不信任客户端（最高优先级）
- 现状：src/app/api/ai/generate/route.ts:25-27,52-53 直接 `const costCredits = credits`（客户端传入）。
- 改法：服务端按 model + 参数独立计价——
  1. 在 models.ts 每个模型配置加服务端计价函数所需字段（baseCredits 取 pricing.json / getBaseCredits()）；
  2. route.ts 增加 `calcCostCredits(model, mediaType, options, configs)`：按 baseCredits × 时长/分辨率/画质倍率计算（逻辑从 video.tsx:325-345 / image.tsx:447-459 移植到服务端）；
  3. 客户端传入的 credits 一律丢弃，仅用于前端展示；
  4. 扣费处（ai_task.ts 事务内）使用服务端计算值。
- 验收：伪造请求传 credits:0 或 1，实际扣费仍为服务端定价；正常请求扣费与前端展示一致。

### SEC-03：Replicate/MUSIC 模型白名单
- 现状：replicate.ts:85-90 任意 model 透传；:269-272 options 全量展开；VIDEO/MUSIC 不送审。
- 改法：
  1. 建 ALLOWED_REPLICATE_MODELS 白名单（从 models.ts 各模型 apiModels 提取）；route.ts 或 replicate.ts 校验，白名单外直接 403；
  2. 透传改白名单字段制：每个模型声明可透传的 options keys，:269-272 改为按声明过滤；
  3. MUSIC/VIDEO 通道文字 prompt 送审（与 SEC-05 同一改动覆盖）。
- 验收：白名单外模型请求被拒；透传字段仅限声明集合。

### SEC-04：admin Server Action 补权限校验（17 处）
- 现状：(admin) 目录 17 处 'use server' 处理器无调用者权限校验，仅页面渲染期校验。
- 改法：
  1. 新建包装器（如 src/lib/admin-action-guard.ts）：`withPermission(code, handler)`，内部调 requirePermission（页面层已有，复用同一权限模型）；
  2. 17 处逐一替换，映射：showcases/categories/prompts/posts 的 add/edit → CONTENT_WRITE；users edit/edit-roles/grant-credits/set-plan → USERS_WRITE；roles edit/edit-permissions → ROLES_WRITE；settings → SETTINGS_WRITE；
  3. 两处 GET 删数据页（如 prompts/[id]/delete）改为 POST + 权限校验，消除 CSRF 面。
- 验收：普通登录用户直接 POST action ID 时被 403；管理员操作正常。

### SEC-10：聊天记录 IDOR（三行修）
- 现状：/api/chat/messages/route.ts:28-35 未校验 chat 归属。
- 改法：查询前取 chat（info 路由 :22-24 同款），`if (chat.userId !== user.id) return respErr('no permission')`；getChatMessages 传入 userId 做二次过滤。
- 验收：用户 A 用用户 B 的 chatId 请求返回无权限。

### 第一批（M1）验证做法

> 前置：本地起服务（或测试环境部署本批改动），准备一个管理员账号、一个普通账号 A、一个普通账号 B。

**1. SEC-02 服务端计价**
- 操作：登录后在工作台正常生成一次图片和一次视频。
- 预期：实际扣费积分与页面展示一致。
- 攻击面验证：用 curl 以登录态伪造 `credits: 0`（或 1）调 `/api/ai/generate`。
- 预期：请求成功但扣费仍为服务端定价，与前端展示一致，不受伪造值影响。

**2. SEC-03 模型白名单**
- 操作：用 curl 以登录态调 `/api/ai/generate`，model 传白名单外的任意 Replicate 模型名（如 `some/evil-model`）；MUSIC 通道传白名单外模型（如 `V999`）。
- 预期：返回报错（model not allowed），不创建任务、不扣费。
- 正常面验证：白名单内模型（google/veo-3.1、openai/sora-2 等）正常生成不受影响。

**3. SEC-04 admin 权限校验**
- 操作：用普通账号 A 的登录态 curl 直接 POST 任一 admin Server Action（如 grant-credits 的 action，目标自己）。
- 预期：返回权限错误（Permission denied），积分未发放。
- 正常面验证：管理员在后台走页面操作（发积分、改配置、改角色等）全部正常。

**4. SEC-10 聊天记录 IDOR**
- 操作：用账号 A 的登录态 curl 调 `/api/chat/messages`，chatId 传账号 B 的。
- 预期：返回 no permission to access this chat，拿不到任何消息。
- 正常面验证：A 用自己的 chatId 拉取消息正常。

**回归（每批改完必跑）**：游客生成、登录生成、余额不足、审核拦截四条路径行为不变。

## 第二批：堵审核入口

### SEC-05：视频/音乐文字 prompt 送审
- 现状：route.ts:76-89 仅 IMAGE+prompt 送审。
- 改法：审核条件去掉 mediaType 限制——IMAGE/VIDEO/MUSIC 的 trimmedPrompt 统一送 moderatePrompt；DeepSeek 审核器 prompt（deepseek.ts:43）从「图片生成提示词审核器」改为通用文本审核器措辞。
- 验收：视频提示词含违规词时请求被拒，图片行为不变。

### SEC-07：KIE 透传排除 prompt（防绕过已审内容）
- 现状：kie.ts:184-201（image）与 :280-294（video）excludeKeys 无 'prompt'，用户可在 options 塞 prompt 覆盖已审值（:151-153）。
- 改法：两处 excludeKeys 增加 'prompt'、'negative_prompt'、'first_frame_url'、'last_frame_url'、'image_urls'、'image_input' 等所有已被单独处理/涉及内容的字段；与 SEC-03 一致，长期改为白名单字段制。
- 验收：options 里塞 prompt 的请求，上游收到的仍是已审字段值。

### SEC-06：参考图片内容审核
- 现状：/api/upload/route.ts:31-40、/api/storage/upload-image/route.ts:43-49 只查 MIME/大小，无内容审核。
- 改法：
  1. 接入图片审核服务（云厂商内容安全 API 或多模态模型），抽 src/shared/services/moderation/image.ts，接口风格对齐 deepseek.ts；
  2. 上传接口在返回 URL 前同步审核，不通过返回 400；带 AbortSignal 超时（吸取 SEC-12）；
  3. 短期止血（接服务前）：对未登录用户关闭参考图上传入口。
- 验收：上传违规图被拒；审核服务异常时上传 fail-closed 并有明确报错。

### SEC-08：重建 IP 风控
- 现状：risk-control.ts:5 引 SQLite schema；login_attempt/ip_blacklist 两表 PG 不存在；catch 后 allowed:true。
- 改法（二选一，推荐 B）：
  - A. 修路径：把两表定义迁入 schema.postgres.ts 并写迁移，risk-control.ts import 改 postgres schema；
  - B. 换实现：删除 SQLite 依赖，改用 PG 一张 risk_event 表 + 限流中间件（SEC-13）承担频控，risk-control 只保留查询。
  - 共同要求：catch 时不再无条件 allowed:true——降级为内存计数限频（rate-limit.ts 已有基础），避免 DB 抖动锁死全站也要避免完全裸奔。
- 验收：同 IP 高频注册/登录被拦截；人为制造 DB 异常时降级为内存限频而非放行。

### 第二批（M2）验证做法

> 前置：本地起服务，管理员后台开启 prompt_moderation_enabled 并配置 DeepSeek key；准备一个管理员账号、一个普通账号。

**1. SEC-05 全媒体送审**
- 操作：在工作台用违规文字提示词分别发起视频生成和音乐生成。
- 预期：两者都被审核拦截并返回明确报错，不创建任务、不扣费。
- 正常面验证：正常提示词的视频/音乐生成不受影响；图片送审行为与改前一致。

**2. SEC-07 透传防覆盖**
- 操作：用 curl 以登录态调 `/api/ai/generate`，prompt 传正常文本，同时在 options 里塞 `prompt: "违规内容"`（走 KIE 通道的模型，如 seedance 系列）。
- 预期：请求到达上游时仍是已审的正常文本；若服务端对 options 中的 prompt 字段直接拒绝更佳。可在日志/任务记录中核对最终提交的 prompt。
- 正常面验证：seedance/gemini/pixverse/minimax 的图生视频、首尾帧功能正常（参考图字段未被误排除）。

**3. SEC-06 上传止血**
- 操作：未登录状态 curl 调 `/api/upload` 与 `/api/storage/upload-image`。
- 预期：返回未登录错误，无法上传。
- 正常面验证：登录用户上传参考图正常（接审核服务后追加：上传违规图返回 400）。

**4. SEC-08 风控重建**
- 操作 A：先跑 `pnpm db:push` 建表，确认 PG 中 login_attempt/ip_blacklist 两表存在；然后同 IP 连续登录失败超过阈值（10 次/24h）。
- 预期：第 11 次起被拦截；ip_blacklist 表出现记录。
- 操作 B：人为停掉数据库连接（改错 DATABASE_URL）再尝试登录。
- 预期：触发内存限频降级（连续失败仍会被拦），而不是无条件放行；日志出现降级告警。
- 正常面验证：正常 IP 登录不受影响。

**回归**：同第一批四条路径；另加「参考图上传 → 图生视频」完整链路。

## 第三批：纵深防御

### SEC-12：审核链路健壮性
- 改法：deepseek.ts:31-54 fetch 加 `signal: AbortSignal.timeout(5000)`；确认生产 prompt_moderation_enabled='true' 且启动时校验该开关与 API key 同时存在，否则打告警日志。
- 验收：审核服务挂起时 generate 5 秒内返回明确错误，不无限等待。

### SEC-13：全局限流
- 现状：仅 auth getSession 一处内存级限流，IP 取 x-forwarded-for 可伪造。
- 改法：引入 Upstash Redis 限流（@upstash/ratelimit），middleware（src/proxy.ts）统一对 /api/ai/generate、/api/upload、/api/storage、/api/proxy/file、/api/payment 按用户 ID（登录）+ IP（游客）限流；阈值按接口敏感度分档（generate 10/min、upload 20/min 等）。
- 验收：超阈值请求 429；伪造 x-forwarded-for 不影响计数（优先用平台真实 IP 头）。

### SEC-09：强制邮箱验证
- 改法：better-auth config 增加 `emailVerification: { sendOnSignUp: true, autoSignInAfterVerification: true }`；登录 session 校验 emailVerified（未验证则拒绝或只读）；上线前置条件：配置 resend_api_key，且 email_verification_enabled 开启（settings.ts:392-395）；灰度建议：先开启发送+软提示，观察一周再强制拦截。一次性邮箱域名黑名单（如 10minutemail 等常见域）作为加分项。
- 验收：新注册用户未验证邮箱前无法生成；验证后正常。

### SEC-14：注册策略收紧
- 改法：依赖 SEC-09 强制验证后假域名号无法激活；如仍有滥用再上：注册邀请码开关（settings 加配置项，默认关）或 OAuth-only 模式（关 emailAndPassword.enabled）。
- 验收：按所选策略，未持邀请码/未走 OAuth 的注册被拒。

### SEC-15：Trial 限领口径（待运营确认）
- 现状：config.ts:122-126 同 IP 前 5 个账号可领（getUsersCountByIp <= 5）。
- 改法：阈值改成后台可配置（settings 加 initial_credits_max_accounts_per_ip，默认 1），代码读配置而非硬编码；注册频控交给 SEC-13。
- 验收：同 IP 第 N+1 个账号不领积分，阈值后台可调。

### SEC-11：SSRF 代理加固
- 现状：/api/proxy/file/route.ts 有 https/私有段校验，但 127.1、2130706433、IPv6（::1、fc00::/7）、302 跟随均可绕过。
- 改法：
  1. 校验改「解析后验证」：new URL → DNS 解析 → 对所有 A/AAAA 记录逐个校验非环回/非私有/非链路本地 → 再 fetch；
  2. `redirect: 'manual'`，每跳复检目标；
  3. 更彻底：仅允许代理本站已上传对象（校验 URL host 属于自己存储域名）。
- 验收： IPv4 简写/十进制/IPv6/302 跳内网均被拒；正常图片代理不受影响。

### SEC-17：Stripe 金额一致性兜底
- 现状：handleCheckoutSuccess（payment.ts:139-247）发放时序正确，但未比对实付金额与订单金额（:162 只记录）。
- 改法：发放前增加 `if (Number(session.paymentInfo.paymentAmount) < Number(order.amount)) { 订单标记异常 + 告警 + 不发放 }`。
- 验收：篡改金额的支付事件不发放积分并留告警记录。

### 第三批（M3）验证做法

> 前置：本地起服务。SEC-12/SEC-15/SEC-09 需管理员后台配置入口；SEC-11/SEC-13/SEC-17 用 curl 即可。

**1. SEC-12 审核超时**
- 操作：把 DeepSeek endpoint 临时指向一个不响应的地址（如本地 `nc -l` 挂起不回包），发起一次生成。
- 预期：约 5 秒内返回明确错误，请求不无限挂起；日志出现审核超时记录。
- 正常面验证：恢复真实 endpoint 后生成正常。

**2. SEC-13 全局限流（待接 Redis 后验证）**
- 操作：以登录态对 `/api/ai/generate` 连续发起超过阈值（10 次/分钟）的请求。
- 预期：超阈值返回 429。
- 伪造 IP 验证：请求头里随便填 `x-forwarded-for: 1.2.3.4` 继续刷，计数仍累加在同一身份上，429 不被绕开。
- 正常面验证：正常节奏使用不触发限流。

**3. SEC-09 强制邮箱验证**
- 操作：用新邮箱注册。
- 预期：注册即收到验证邮件；验证前无法生成（软提示阶段则只提示不拦截）；点击验证链接后恢复正常使用。
- 观察项：一周内验证邮件送达率正常（进收件箱而非垃圾箱）后再收紧强制拦截。

**4. SEC-14 注册策略（按启用策略验证）**
- 邀请码模式：无邀请码注册被拒，持有效邀请码注册成功。
- OAuth-only 模式：邮箱密码登录入口关闭，第三方登录正常。

**5. SEC-15 Trial 阈值可配置**
- 操作：管理员后台把 initial_credits_max_accounts_per_ip 改为 2；同 IP 注册第 3 个账号。
- 预期：第 3 个账号不领初始积分，前 2 个正常领取；改回 1 后第 2 个即不领。

**6. SEC-11 SSRF 加固**
- 操作：登录态 curl 调 `/api/proxy/file`，url 分别传：`http://127.1/`、`http://2130706433/`、`http://[::1]/`、`http://[fc00::1]/`、`http://内网IP/`，以及一个 302 跳转到内网地址的外部 URL。
- 预期：全部返回拒绝（private address not allowed），不发起实际请求。
- 正常面验证：代理一张正常公网图片（工作台生成结果图）能正常返回。

**7. SEC-17 金额一致性**
- 操作：在 Stripe 测试模式用 webhook 校验签名不变、但篡改 amount（实付 < 订单金额）的 checkout.session.completed 事件。
- 预期：订单标记异常、不发放积分，日志出现金额不一致告警。
- 正常面验证：测试模式走一次正常支付，积分正常发放。

**回归**：同前两批四条路径，另加「Stripe 测试模式完整支付 → 发放 → 生成」链路。

## 收尾项

### SEC-01（顺手项）：.env.example 脱敏
- 改法：DATABASE_URL 改 `postgresql://user:password@host:5432/db`，AUTH_SECRET 改 `openssl rand -base64 32 生成的占位符`，其余真实值全部占位化。旧站已死，无紧急性，纯模板卫生。
- 验证方式：全文搜索确认无真实密钥/连接串残留（对照 .env 逐项核对，凡 example 里出现的值不得与 .env 相同）；新环境按 example 配置能正常启动。

## 验证与回归

- 每批改完跑一次生成主流程回归：游客生成、登录生成、余额不足、审核拦截四条路径。
- 资金类改动（SEC-02/03/17）必须写一条 API 级测试（项目当前无 auth/risk 测试，从这批开始建立 tests/ 基础）。
- 上线顺序建议：先 SEC-04（纯加校验，零行为变化风险）→ SEC-02 → 其余。
